Contents

Introduction

Asterism shows the AI setup on your computer as cards and as a map: which coding agents are installed, which language models they use — cloud services and local runtimes — the models those serve, and which MCP servers and skills each agent has. And it lets you change that setup by drawing lines.

The main window: the map across the whole width, the GPU card above it, the ! for open problems in the header.

What it does

  • Coding agents — Claude Code, Codex, GitHub Copilot, Cursor CLI, Gemini, OpenCode, Pi, Hermes and more: their version, plan, limits and usage, and what each one still needs, with the command that fixes it.
  • Local LLMs — llama.cpp, Ollama, LM Studio, vLLM, Jan and KoboldCpp: install them, download models, set the context size that fits your graphics card, and start them together with the agents that use them.
  • MCP servers and skills — found on your computer or on the web, with recommended servers and a search of the official MCP registry.
  • Open problems — a ! in the header when something needs fixing, each problem with the way to where it is fixed, and what your setup is good for.

Key ideas

Agent
A program you talk to that writes code or does tasks, such as Claude Code.
LLM provider
Where an agent's model runs: a cloud service (Anthropic, OpenAI, …) or a local LLM runtime on this computer (llama.cpp, Ollama, …).
Model
The language model itself. Local models are files, usually in GGUF format.
MCP server
A small program or web service that gives agents extra tools — reading files, searching the web, controlling a browser. MCP is the Model Context Protocol.
Skill
A folder with instructions (a SKILL.md) and sometimes scripts that teach an agent how to do a particular job.

Nothing changes without a preview

Every change to an agent's settings is shown first, line by line, before anything is written. The old file is kept as a backup, and the bar that appears after the change has Undo. The app itself never runs with administrator rights; only installing an agent that comes as a system package asks for your password, in a terminal you watch.

Installation

Asterism Asterism

Choose one of these ways:

  • Arch Linux (AUR): install the package asterism with your AUR helper.
  • AppImage: download Asterism-<version>-x86_64.AppImage from the releases page at github.com/uBruckhaus/Asterism, make it executable and run it. The AppImage uses your distribution's Python 3 with PyGObject, GTK 4 and libadwaita:
    Fedorasudo dnf install python3-gobject gtk4 libadwaita
    Ubuntu / Debiansudo apt install python3-gi gir1.2-gtk-4.0 gir1.2-adw-1
    Archsudo pacman -S python-gobject gtk4 libadwaita
  • From source: run bin/asterism in a checkout of the repository.

The app brings its own icons, so no icon font is needed. To run agents inside the window, also install VTE for GTK 4 (vte4).

AI Agents Map on Omarchy Omarchy

Install the plugin from the Omarchy Plugin Marketplace, or from a terminal:

omarchy plugin add https://github.com/uBruckhaus/omarchy-ai-agents-map.git --enable

A robot button appears in the bar. Everything else it needs comes with a standard Omarchy install. To run agents inside the window, install VTE: sudo pacman -S vte4.

First start

On the first open, the app asks whether to add itself to the app launcher. Nothing is written there unless you say yes; you can change it later in Settings › In the app launcher.

The window is a normal app window: it can be tiled, floated, moved to another workspace and reached with Alt+Tab. Asterism A fresh Asterism opens on its welcome page: the agents and local LLMs installed on this computer are cards that are already ticked, and Switch on puts them on the map (see Setting up Asterism). Omarchy The bar button opens the window, brings it to the front, or hides it when it is already in front. Closing the window hides it; the program keeps running in the background so it opens again at once.

Note While an agent runs inside the window, closing it asks first: Stop and close (the agent's local LLM then stops too and frees the graphics card's memory) or Keep running.

Removing the app

Omarchy omarchy plugin remove ubruckhaus.ai-agents-map. Asterism Remove the package or delete the AppImage.

Before removing, switch off Settings › Start local LLMs with their agents so the background watcher is removed too, and Settings › In the app launcher to delete the launcher entry. Changes you made with the app stay: agents' settings, MCP servers, skills and installed local LLMs. Uninstall a local LLM first (right-click › Uninstall…) if you want it gone. To delete the app's own state as well:

rm -rf ~/.config/omarchy/ai-agents-map ~/.config/asterism \
       ~/.local/state/ai-agents-map ~/.cache/ai-agents-map

Setup

The map shows only what is set up: installed agents and local LLMs, the MCP servers and skill folders agents use, and models. Everything else is done on Setup (the button in the header, beside Map), one card per item, in sections that fold away with a click on their bar:

  • How things get onto your map — a folded card at the top; open it for five numbered steps: switch on (or find) what you use, install what is missing, sign in to an online agent, connect by drawing, and what shows up by itself.
  • What you can do with this — what the setup is good for (everyday help, coding, images, voice, research and writing), one tile each with what is there and the next step; folded, its line says how many are ready.
  • AI agents, Local LLMs — every one the app knows. A card with a blue frame is installed on this PC; a grey one is not, and has Install where installed ones have Uninstall. Omarchy A click on an installed card opens its details. Asterism A click ticks or unticks the card (✓), then Apply switches its add-on on or off. Switching off takes it off the map; nothing is deleted.

  • MCP servers, Skills, Models — a card for each one that is installed. A click opens its details (a model: its menu). The card with a + at the end of a section adds one: Add MCP server, Add skills, Add model, Get add-ons.
  • ⋯ or a right-click on a card opens the same menu as the box on the map: update, sign in, start or stop, details, uninstall or remove, move a model.
  • A yellow ↑ version on a card means an update is waiting; its menu has Update.
  • A red ! on a card means an open problem there; hover it for what it is.
  • A small battery on an online agent's card shows what is left of its limits (a session, a week): the tightest one counts, yellow at a quarter or less, red under a tenth; hover it for each limit and when it resets. On a running local LLM's card the battery is the GPU memory still free, with the same colours; hover it for how much that local LLM uses.

Choosing what the map shows

The map shows everything that is set up. The Show toggles below the GPU card leave whole categories out of it — for example all skills, or the local LLMs and their models — and are remembered.

In a narrow window (half the screen or less) the map chooses them itself, and a line beside the toggles says so: while an agent runs, agents and providers (who works through what); while none runs, providers and models. A toggle clicked there stays until that changes and is not remembered; the full-size window keeps your own choice.

Working with the map

  • Hover a box to light it up together with everything it is joined to.
  • Click a box to select it (✓); Shift+click adds more. Esc or Clear selection clears it.
  • The pin at a box's top-right corner keeps its connections lit while you look elsewhere.
  • Right-click a box for everything its card on Setup offers: start or stop, details, install, sign in, models, update, remove, and more.
  • ▶ on an agent's box starts it in a terminal in the window.
  • The agents always stay in the middle of the map's visible part while you scroll.
  • Each agent's active path — agent → provider in use → its model — is drawn bold. While an agent is working, light runs along that line.
  • A red dotted line joins an agent to a provider it is set up for but does not use now (no model of it in use).
  • An online agent's box has the same battery as its card on Setup: what is left of its limits; a running local LLM's box, the GPU memory still free.
  • When a program that is not on the map uses a local LLM, the line from that LLM to the model turns bold in a colour of its own (purple or cyan, whichever stands out from the theme's other colours), and light runs along it. See Used by other apps.
  • The refresh symbol (F5) at the right of the heading looks again at what is installed, set up and signed in.
  • Until the first line is drawn, a card above the map shows how, in three steps; Watch how plays the animation from Help. It goes for good after the first connection, or with ×.
  • Zoom with − 100 % +, Ctrl+scroll or Ctrl++ / − / 0.

Tip In a narrow window (below about 1300 pixels, such as half the screen) the map scrolls sideways, and Maximize for more room in the header gives it the whole screen (Settings › Too narrow for the map chooses what that button does).

Open problems

When something needs fixing, a red ! appears among the header's symbols; its tooltip says how many, for example 2 open problems · 4 suggestions. A click opens Open problems: one line each — an agent not signed in, a local LLM without models, a connection that does not work, little free space for models — with a button to where it is fixed (the agent's or local LLM's details, the map with that line lit, Setup, Tidy up). The same problems show as a red ! on their cards on Setup. Tips and what works are on the cards and details pages themselves, and what the setup is good for is on Setup (What you can do with this). The check only reads; it never changes, starts or sends anything, and it shows nothing while the map is still empty.

Updates and suggestions

Below the problems on the same page, Updates and suggestions lists what there is to say: new programs or skills found on this PC, what is on this PC but not on the map, and updates for installed agents and local LLMs, each with its button (Add MCP server…, Setup, Update). With only these and no problem, the header's ! shows in the accent colour. Updates are checked in the background when the window opens, at most every six hours. Nothing is installed by the check itself; an update starts only when you click Update.

Agents

Agent details

Every coding agent has a card on Setup, installed ones with their version. Click an installed agent's card (Asterism or ⋯ › Details), or right-click its box on the map › Details. At the top, one line says whether the agent is ready (and if not, why) and whether it is running now or when it was last used. Below it, every category is a card that folds: click its heading to open or close it. They start folded, each with a one-line summary and badges; a category you open stays open on the next details pages.

Starting and stopping agents

  • ▶ on the agent's box, or Start here in its menu, runs the agent in a terminal inside the window, in place of the map. This needs VTE (vte4).
  • Start in terminal opens it in a terminal window of its own.
  • While it runs inside the window: Show terminal and Stop. Stop ends the agent and everything it started, such as its MCP servers.

When agents have terminals in the window, a tab line above the map shows one tab per terminal with a dot for working, running or ended. Click a tab to show that terminal; × closes an ended one.

An agent with an open instance anywhere on the computer gets a green dot and running, and the model box it runs with says in use · <agent>.

AI Playground

Chess and other tests with your agents are in an app of their own: AI Playground. It lets an agent play chess against you (or two agents against each other), compares speed and cost, judges two answers blind, tests pictures and video frames, and asks your local LLMs. It uses the agents that are set up here.

When AI Playground is installed (the Omarchy plugin, or the ai-playground app on other desktops), its button, a gamepad, appears in the header. Select an agent on the map first, and AI Playground opens with that agent chosen. On Omarchy the ⓘ Information page tells more about it and links to its page in the Omarchy Plugin Marketplace.

Signing in

Sign in… in an agent's menu (on Setup or on the map) shows what the agent needs and its own ways to sign in:

  • A subscription or an account — the agent's own sign-in runs in a terminal in the window (for example claude auth login or codex login). Your password or browser login stays between you and the agent; the app never sees it. Where the agent asks for it, the terminal says what to type (Pi and Copilot: /login).
  • An API key — for agents that read one: the key goes into a password field, then straight to the agent's own command (Codex stores it itself) or into the file the agent reads (Gemini: ~/.gemini/.env, readable only by you). It never goes into a command line, a log or the app's settings, and the app does not keep it. Claude Code's API billing is its own Anthropic Console sign-in, so no key passes through the app.

Signing in to Claude Code: a subscription or API billing, both with Claude Code's own sign-in.

Afterwards the map shows the agent's online provider and its models.

Updating agents

When a newer version of an installed agent is out, its card on Setup gets a yellow ↑ version, and Updates and suggestions (the header's !) names it. Update runs the update the same way the agent was installed — for example mise upgrade <tool> or claude update — in a terminal window of its own, so you can follow it.

Agents the app can install

Three agents can be installed, updated and uninstalled from the map (right-click the agent › Install…):

  • DeepSeek Harness (dsh, developer preview), from npm. It can use local LLMs.
  • Antigravity CLI (agy, Google), from Google's release manifest; the download is checked against its SHA-512.
  • LM Studio Bionic cannot be installed from here (no published checksum); get it from lmstudio.ai. It always uses LM Studio's engine and models.

New agents

When an agent turns up that the app does not know yet, it asks an installed agent (Claude Code, else Codex) once to find out on the web where that agent keeps its skills and MCP servers. The answer is checked before use, and nothing in it is ever run. Settings › Look up new agents switches this off.

Local LLMs

A local LLM runtime runs language models on your own graphics card, so prompts never leave the computer. The app installs, starts and stops them for you.

Installing a local LLM

Right-click a grey (not installed) local LLM on the map › Install…. You choose the program folder, the model folder (the one your other local LLMs use is suggested) and whether it starts at login. It is installed for your user only, with a user service, so no password is needed. Every download must match the SHA-256 checksum its release publishes before it is unpacked or run.

RuntimeNotes
OllamaThe official release (with ROCm for AMD cards).
llama.cppThe build of your choice (Vulkan, ROCm, CUDA, CPU), run as a model router: every GGUF in the model folder, one loaded at a time.
LM StudioNot installed from here (no published checksum); get it from lmstudio.ai. Shown and managed once installed.
vLLMFor NVIDIA cards, in its own Python environment.
JanIts AppImage, unpacked, with Jan's engine as a background service for agents.
KoboldCppThe official single-file build, run as a model router.

Installed this way, a local LLM also offers Update… (the previous version is kept as a fallback), Model folder… and Uninstall…, which removes the program, command, service and settings but never the models. Local LLMs you installed yourself are shown, but never changed.

Starting and stopping with agents

Connect an agent to a local LLM once, then just start the agent — even with the app closed or after a reboot. Its local LLM starts with it, and when the last agent using it closes, the LLM stops about five seconds later, so its graphics memory is free again.

A small background service, ai-agents-map-providers.service, does this. It is set up with the first connection to a local LLM and removed when the last one goes, or when you switch off Settings › Start local LLMs with their agents.

Note KoboldCpp takes a few seconds to start, longer than some agents wait. So it starts at login, and when the last agent closes only its model is unloaded.

A local LLM's details

Click a local LLM's card on Setup, or right-click its box on the map › Details. Below the tiles (models, agents, address) the same folding cards as for agents: Usage and tokens — what your agents sent through it in the last days, per agent and model, taken from the agents' own session numbers and matched by model name — then Health, Risk management, What the words mean and Configuration.

GPU memory and Free GPU memory

In the GPU card above the map, GPU memory shows how much is in use, split into local LLMs, desktop and apps, and free; GPU activity shows load, temperature and power. Each local LLM's box shows how much memory it holds, and loaded models get a green dot.

Right-click a local LLM for Start, Stop, start at login, and Free GPU memory: its models are unloaded, it keeps running and loads one again when asked.

A local LLM that holds GPU memory gets a red stop button on its box. It asks first: Free GPU memory unloads its models; Stop ends it. For LM Studio the button is Stop server: only its server ends, and the app stays open with its models loaded. A model that a local LLM has loaded, but no agent uses, is joined to it by a solid light line.

LM Studio can be open without its server. Its box then says server off with a yellow dot, agents cannot reach it, and its menu offers Start server (lms server start).

Used by other apps

Local LLMs are not only used by agents. A plugin such as Video Trans, a chat app or your own script can send requests to them too. The app notices this and shows it:

A program that is not on the map (here curl) generating with llama.cpp: the cyan line and box (Tokyo Night theme). Claude Code's own path to opus stays in the accent colour.

  • On the map, the line from the local LLM to the model it is generating with turns bold in its own colour, light runs along it, and the model box gets a frame and dot in that colour and says who is using it, for example in use · Video Trans.
  • The local LLM's right-click menu and its ⓘ Details page say In use by Video Trans · now, or how many seconds ago it was last used.
  • The ⓘ legend shows both marks.

The app looks at which of your own programs have a connection open to the local LLM. It never reads what they send. A plugin is named by its own name, an agent by its name, anything else by its program name. The app itself and LLM Monitor, which only read the status, are not counted.

Note The light shows only while the program is generating, and fades about ten seconds after its last request. A program that is open but idle — Video Trans with no speech to translate — shows nothing. A program stays listed in the menu for half a minute after its last request.

Models

Right-click an installed local LLM › Models…, or click Add model on Setup. The page has a list on the left and the chosen model on the right, in three tabs.

Get from Hugging Face: what a model can do, and which size fits your graphics card.

Get from Hugging Face

Browse the trending GGUF chat models or search. Each result shows its author, size, downloads, likes, age and what it can do: Vision, Tools, Reasoning, MTP. The model's page shows its parameters, architecture, context, license and model card. What the name means explains the parts of the name, such as 35B-A3B or Q4_K_M.

Download options lists every size with how it fits: in the graphics card, partly in system memory (works, but slower), or likely too large. The best fit is chosen for you; Download gets it into the model folder.

Downloads run in the background and show in a strip at the top of the main page. A broken connection is retried and the download resumes. If the app was closed during a download, it is listed as interrupted, with Continue or Discard.

Installed

Installed: context now, best for your card and trained for; what the name means; Remove.

Each model shows its size, file and context — now, best for your card and trained for. Remove asks first and moves the files to the trash, where you can restore them. A model that is only a link loses only the link.

Context size

The context is how much text the model can keep in mind at once. The app calculates the largest context that fits your graphics card from the model file itself. Set context writes it to the local LLM's settings, with a backup and Undo. Agents need a fairly large context; when you connect an agent to an LM Studio model without a context set, the best one is set in the same step.

On this PC

Lists GGUF files the local LLM does not read yet — in its models folder, the other local LLMs' folders, ~/Downloads and ~/Models. Add makes one its model without a second copy (a link), except for Ollama, which imports its own copy.

Moving and deleting models

Right-click a model of llama.cpp, KoboldCpp or LM Studio › Move to…, or drag the model box onto another local LLM's folder. First you see how much moves and which agent uses the model. Undo moves the files back. Delete… asks first and moves the files to the trash.

One models folder

Settings › Models folder sets one folder for every local LLM's models. Reorganize models… previews how the files would be sorted (<folder>/<publisher>/<model>/), and nothing changes until you press Reorganize. With Keep old paths working (on by default), a link stays at every old place. Undo the last reorganize puts everything back.

Caution Moving models to another disk copies them first and removes the originals only when the copy is complete. Make sure the target disk has enough free space; the app refuses the move if it has not.

Connecting by drawing

Press on a box on the map and drag to another to connect them. Every change shows exactly which lines of which file change before anything is written, keeps a backup, and can be undone from the bar that follows.

Agent ↔ local LLM

Drag from an agent to a local LLM, or back. Choose the model and whether the agent uses it right away. To change a connection, click the line to select it, then drag its end to another local LLM — or onto empty space to remove it. With an agent selected, clicking a model of a connected local LLM makes that model the agent's model.

Supported agents: Hermes, Pi, OpenCode and DeepSeek Harness.

Agent ↔ MCP server

Drag from an agent to an MCP server. The server's settings are copied into that agent's own format. Supported: Claude Code, Codex, Copilot, Crush, Cursor, Gemini, Grok, Hermes, Muse, Oh My Pi, OpenClaw, OpenCode and Pi. Settings files that may hold keys are always written so that only you can read them.

Agent ↔ skill folder

Drag from an agent to a skill folder. Pi and Hermes get the folder in their settings; every other agent gets one link per skill in its own skills folder. A folder an agent reads by itself (most read ~/.agents/skills) cannot be taken away from just that agent.

When a connection fails

Right after a connection is written, the app checks whether it will work: whether a local LLM is installed and offers the model, whether an MCP server answers, whether the skill links are intact. A connection that fails stays on the map as a dotted red line with a !; one with only warnings is dotted yellow. Click the line or its ! for hints:

  • Test again checks once more; when it passes, the line becomes normal.
  • Try again… opens the connect page for a connection that was never written.
  • Remove connection removes it.

MCP servers

MCP servers give agents extra tools. + MCP server on the map or under the cards opens the page for adding one: a list on the left, the chosen server's page on the right.

Setting a server up

The server's page says who made it and how well that is checked, what it does (with things to ask an agent once it has it), how it runs — a program through npx, uvx or Docker, or a web service — and what it needs, such as a folder or an API key with a link to where you get one. Below it, Set it up:

  1. Fill in the fields the server needs.
  2. Tick the agents that should get it.
  3. Click Test to ask the server for its tools.
  4. Click Add: all ticked agents are written at once, with one preview and one Undo.

Note Secret values such as API keys are passed in the environment or in headers, never on a command line where other users of the computer could read them. A server that would need a secret on its command line has to be set up by hand.

Managing servers

ⓘ Details on an MCP server card shows each agent's settings file, the command or address, and on request the server's tools; values of keys are never shown. Remove takes the server from every agent. Servers stay in the list when no agent uses them any more, so a line can connect them again.

When a newer version of an app that provides an MCP server turns up in ~/Applications, a note names it. Update… unpacks the new version, points every agent at it and keeps the old one as a backup for seven days. Check for updates (in On this PC) does it for every such app at once after your click: it looks inside the new versions, offers all updates in one preview with one backup and one Undo, and then tests each updated server; a note names any that does not answer.

Skills

A skill is a folder with instructions that teach an agent a particular job. + Skills opens a page laid out like the MCP page.

Finding skills

  • On this PC: skill folders that apps brought along and no agent reads yet.
  • From the web: a search of the skills.sh directory, another site with the same API, or a GitHub repository with skills. A skill is fetched from its GitHub repository into a folder of your choice, by default ~/.agents/skills.

Caution Skills can contain scripts that an agent may run later. The page shows the repository and lists the scripts before anything is fetched — check them.

Skill folders

Each skill folder card shows its skills and the agents that read it. A folder that is shared through links shows up once, where it really lives. ⓘ Details lists every skill with its description and how each agent gets the folder.

Settings

Healthy & Security check

A coding agent reads and writes files and runs commands on your computer. How much it may do without asking you is set in the agent's own settings, with different words in every agent. The Healthy & Security check brings this together: on the details page of every agent and of every local LLM, four cards show whether it works, what it may do, what that means in plain words, and what lowers the risk.

OpenCode's Security settings, with Run commands opened, and the start of its Risk management.

Reading the cards

The badges on the folded cards sum it up: Healthy, Needs a look or Not set up on Health, and Low risk, Medium risk or High risk on Security settings and Risk management. Open a card for its details:

CardWhat it shows
HealthEvery setup check with a ✓, or what to do next: installed, signed in, its model and local LLM, MCP servers and skills.
Security settingsThe agent's settings that decide what it may do on its own, each with its value now and one sentence on what that means. The mark in front tells the risk: ✓ safe, · low, a yellow ! medium, a red ! high.
Risk managementWhat the settings mean together, most serious first, each with why it matters and → what lowers it. Protections that are in place are listed with a ✓.

Allow and deny rules and trusted folders the agent has (for example Claude Code's permissions.allow list) are listed below the settings, one rule per line.

Changing a setting

  1. Click a setting to open it. You see what it controls and every choice, each with its risk; the one in use is marked In use, the safer default recommended.
  2. Click Use… beside a choice, or Lower it… beside a risk. A page shows the change in words (old → new), the risk before and after, and What changes: the lines of the agent's settings file.
  3. Click Change. The file is backed up and written; a message offers Undo for 30 seconds. The agent uses the new setting the next time it starts.

Note Only the one key changes; comments and everything else in the file stay as they are. A setting that needs more than a line in a file — such as Hermes running its commands in Docker — is shown and explained, with where to change it, but not changed from here.

Managing the risk

The risk level is the most serious point the card finds:

  • High risk — it can do serious things without asking: run any command, or work with no sandbox and no questions. Fine in a throwaway container or virtual machine; on your own PC, let it ask first.
  • Medium risk — some things happen without asking, such as editing files in the project, or an automatic review decides for you.
  • Low risk — it asks before anything that matters, or cannot do it at all.

Good habits, whatever the settings:

  • Ask first for commands on your own computer; allow single, harmless commands (such as git status) with an allow rule instead of allowing the whole shell.
  • Switch the sandbox on where the agent has one (Claude Code, Codex, Cursor CLI), and leave the network in it off unless a task needs it.
  • Start agents in the project folder, not in your home folder, and keep keys and passwords out of it.
  • Keep MCP servers few: only the ones you use and trust. Each runs with your rights.
  • Run unattended work (bypass mode, “YOLO”, Pi with all tools) in a container or virtual machine.
  • Local LLMs on 127.0.0.1: their servers have no password.

Caution An automatic review (Claude Code's auto mode, Copilot's assisted, Cursor's auto-review, Hermes's smart) is a second AI judging each step. It saves questions, but it is a judgement, not a wall.

The words explained

What a sandbox changes: commands reach only the project folder and what you allow.

Sandbox
A fenced-off area the agent's commands run in. Inside it a command can touch only the project folder (and what you allow) — not the rest of your home folder, your SSH keys or browser data, and often not the internet. Without one, a command the agent runs can do anything you can.
Approval (asking first)
Before the agent edits a file or runs a command, it shows what it wants to do and waits for Yes or No. The less it may do without asking, the more control you keep, and the more often you are asked.
Allow and deny rules
Lists of commands or tools the agent may use without asking (allow) or never (deny). Deny wins over allow. A rule that allows every shell command switches approval off for the shell.
Trusted folder
A folder you said the agent may work in. There it also uses the folder's own instructions and settings, which can come from someone else when you clone a project.
Network access
Whether commands may reach the internet. Code that reads your files and can send data out could leak them; installing packages needs the network too.
Bypass (“YOLO”)
Everything without asking and without limits. Only for a throwaway virtual machine or container.
Automatic review
A second AI model lets harmless actions through and asks about the rest.
Prompt injection
Instructions hidden in a web page, file or tool answer that try to make the agent do something you did not ask for. Asking first, a sandbox and no network stop it.
Secret redaction
Text that looks like a password, token or key is masked before the model sees it or it reaches a log.
Tools
What the agent can do at all: read, write, run commands, search the web. A tool it does not have cannot be misused.
MCP server
A small program that gives the agent extra tools. It runs as you, with your rights.
127.0.0.1 (localhost)
An address only programs on this PC can reach. A server on 0.0.0.0 can be reached from every device on your network.

Add-ons

Everything Asterism understands about an agent or an LLM provider is an adapter: how it is found and installed, its sessions, security settings, MCP servers and skills. In Asterism every adapter is an add-on: the packages bring all of them, signed and switched off, and you switch on the ones you use. Add-ons also bring new agents, new providers, and features beyond the numbers, such as Insights (session topics and a summary by Claude). The AI Agents Map plugin has the adapters built in and no add-ons.

Setting up Asterism

A new Asterism opens on its welcome page. Every agent and local LLM Asterism knows is a card with its own icon, in three groups: AI agents, Local LLMs and Online providers (the names of Anthropic, OpenAI and the others on the map). Each card says whether the program is here:

  • Installed (green) — found the same way the map finds it; the card is already ticked;
  • Used before — not installed now, but its settings are still here;
  • Not installed — tick it to install it afterwards from its card.

The welcome page: found programs come first and are ticked.

Click a card (or press Space on it) to tick or untick it; a ticked card has a blue frame and a check mark. Switch on (with the number of ticked cards) loads them and shows the map; when you ticked programs that are not installed, Setup opens: ⋯ on their cards › Install…. Later starts with an empty map. As long as nothing is switched on, Asterism opens on the welcome page again at every start. Afterwards the same cards are on Setup (the header button), where agents and providers are switched on and off at any time.

The Add-ons page

Open it with the puzzle button in the header, from Settings › Add-ons, or from any "add-on available" hint. It shows, as cards:

  • Suggested for this PC — an add-on whose agent or provider is installed here but not shown yet;
  • Installed add-ons — on, off, or not loaded with the reason (for example a changed file);
  • Available — the other add-ons of the catalog;
  • Built into Asterism — agents and providers that no installed add-on brings (when you run Asterism from its source folder without add-ons).

Installed add-ons: on or off, with Install and Uninstall for the program.

The card of an agent or local LLM that is switched on has Install and Uninstall for the program itself (the one that does not apply is greyed out), and every card with a homepage has a globe button that opens it in your browser.

Search finds names, descriptions and what an add-on reads; the chips above narrow the list to agents, providers, features, the installed ones or those with an update. Click a card for its details: what it reads, what it sends, what it may do, and its privacy level.

Installing, switching on and off, updating, removing

Install (or Get add-on) first shows what the add-on reads, sends and may do; only after your OK is it downloaded, checked and switched on. Switch off and Switch on work at once, without a restart: its agents, providers, sections and cards appear or disappear everywhere. Update replaces it with the newer version from the catalog, after the new one was checked; Remove moves it to the trash. Install from file… takes an add-on zip you downloaded yourself; the same checks apply.

Only from the author. Asterism loads only add-ons signed by Uwe Bruckhaus (key fingerprint SHA256:e5cC634Ke3Our5LAeSc88qs22NKZEHTncBW5Ig3amWQ). Before anything of an add-on runs, the signature is checked with OpenSSH's ssh-keygen, every file is compared with its SHA-256, and no file may have been added. A download must also match the SHA-256 in the signed catalog.

KindWhat it brings

A new agent on your computer

When you install an agent Asterism does not know yet, it looks in the catalog (Settings › Look for add-ons online, on by default: the list is read from GitHub every few hours, nothing is sent but the request). If an add-on knows that agent, Updates and suggestions (the header's !) says so ("Kilo Code is on this PC but not on the map") and a card under Suggested for this PC; one click installs it. If no add-on exists yet, the agent's details say so, with a link to ask for one.

Privacy and safety

  • No administrator rights for the app. It never runs as root and never sees a password. Installing an agent that comes as a system package (such as Hermes or OpenClaw) runs the system's package manager through sudo in a terminal you watch, after showing you the command.
  • No credentials read. It reads the agents' settings, but never their credential files. Whether an agent is signed in is judged from whether such a file exists. Values of keys and headers are never shown.
  • No conversations read. Usage figures are read as numbers and times only.
  • Network only when asked — searching models, MCP servers or skills, installing, testing a server — plus an update check every few hours.
  • Checked downloads. Programs are installed only when the download matches the checksum its release publishes.
  • Previews and Undo. Every change to another program's settings is previewed, backed up and can be undone. Settings that may hold keys are written readable only by you.
  • Bounded. Every program runs without a shell, and every answer is read with a size and time limit.

The README in each repository lists in full what is read, started and written.

Glossary

Approval
An agent asking before it changes a file or runs a command (see The words explained).
Context
How many tokens of text a model can keep in mind at once.
GGUF
The file format for models used by llama.cpp, LM Studio, Ollama and KoboldCpp.
Prompt injection
Hidden instructions in a page, file or tool answer that try to steer an agent.
Quantization
Storing a model with fewer bits per weight (for example Q4_K_M, about 4.8 bits) so it is smaller, with a small loss of quality.
Mixture of experts
A model where only part of the parameters work for each token (35B-A3B: 35 billion in all, 3 billion active), which makes it fast for its size.
Sandbox
A fenced-off area an agent's commands run in, reaching only the project folder and what you allow.
Token
A piece of text, roughly three quarters of a word, that models read and write.
User service
A background program started by systemd for your user only, without administrator rights.
